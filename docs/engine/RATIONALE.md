# Rationale

## Problem

One Swift package has to serve four very different callers: a widget extension with about 30 MB and no time to spare, an App Intent that writes from that same process, an on-device builder that turns untrusted model output into a saved widget, and a Mac command line tool for evals. Each widget is half closed blocks (typed tables, a closed query set, a closed action set, server automations) and half AI-written JavaScript that returns a view tree. Several constraints make the shape non-obvious. Two processes write one SQLite file. A later per-field LWW sync must not force a rewrite. Day windows need a clock and calendar while the look must stay pure. A runaway look must stop without taking the extension's thread or memory with it, which JavaScriptCore cannot do, so looks run on an embedded engine with step and memory budgets. The renderer must turn a button into an App Intent in one host and into nothing in another. And the backend runs on Cloudflare Workers, so fit, which needs SwiftUI layout, can only be measured on Apple hardware. That puts the build loop in the app, not on the server.

Starting stance: the smallest public interface. It held. Each entry point is one call on one noun, `Engine`. I departed from a literal single module in two places, both explained under Shape: build capabilities arrive through a second import that the extension never links, and a small `WidgetHosting` target holds the App Intents and WidgetKit glue because the app and the extension must compile identical intent types.

## Usage (caller's view)

Full call sites are in [USAGE.md](USAGE.md), written before the types. In short:

```swift
let faces = await engine.faces(for: id, family: .small, size: context.displaySize, from: .now)   // timeline provider
FaceView(faces.current, host: .widget)                                                            // entry view

try engine.perform(Tap(widget: w, revision: d, action: a, row: r))                               // App Intent
try engine.perform(form.tap, input: ["title": .text("Buy oat milk")])                            // app, after a form link

switch try await engine.build(reply, replacing: id) { case .saved(let id): ...; case .rejected(let line): ... }   // builder

let proof = try await Engine.proof(try WidgetSource(directory: dir), state: .full, family: .medium)   // render tool
```

## Shape

**Interface depth.** The public surface is `Engine` with five runtime methods (`faces`, `perform`, `form`, `widgets`, `delete`), the static `suspend` and `resume` for the process lifecycle, and seven builder methods (`build`, `proveReceived`, `source(of:)`, `history(of:)`, `restore`, and the static `proof` and `proofs`), plus plain value types and one view. Behind it sit the SQL schema and migrations, content-addressed revisions, the hybrid logical clock and merge, query compilation, calendar arithmetic, the JavaScript engine and its purity prelude and step and memory budgets, context encoding, a tree grammar of 13 node types and about 40 props, validation, image decoding, the renderer, the geometry probe, fit analysis, the synthesized proof states, verdict lines, image ingest, and format upgrades. No caller coordinates two calls to finish one operation. No option exposes an internal stage. The one public input that is raw on purpose is `WidgetSource` (JSON bytes plus image bytes), because that is where untrusted text enters, and it is parsed inside (per boundary-discipline).

**Three capability sets, one noun.** `WidgetEngine` declares `Engine`. `WidgetBuilder` adds `build`, `proveReceived`, `source(of:)`, `history(of:)`, `restore`, `proof`, and `proofs` by extension. The app imports both, and the extension imports only the first, so "the widget extension never ingests a photo, encodes a PNG, or runs fit analysis" is a link-time fact rather than a convention. `Spec`, `Rows`, and `Sandbox` are package-internal targets with no public declarations, so app code cannot reach them (red flag: importable internals). `Engine/scripts/check` fails the build on a stray `public` there.

**The widget document.** One exchange format, `widget.json` plus image bytes keyed by asset id. It is the model's reply, what `source(of:)` returns for refinement, the render tool's input, a debugging export, and what a second user receives. A saved document is an immutable revision named by the SHA-256 of its canonical bytes, and the widget record points at its head revision. A refinement adds a revision and moves the head, which gives "undo that change" for free and makes sharing a matter of fetching a revision by hash. For the hash to name everything a revision needs, the document itself carries what the model does not write: each asset's digest and each automation's time zone. The builder fills both before saving. Canonical encoding sorts keys and writes every default, so equal documents always hash equal. Versioning has two axes. `format` is the grammar version: older documents are upgraded step by step on raw JSON at parse time, stored bytes are never rewritten, and a newer format is refused up front. The look vocabulary is append-only, since look code cannot be migrated. A refinement keeps one compatibility rule: every table id and every field id survives, and a field keeps its kind, because rows are bound to the table id and cells were written under the field id with that kind.

**Dangling references and type mismatches** are unrepresentable after `Spec.parse` (per encode-lessons-in-structure). References resolve to typed handles. A field is `Spec.Field<V>` with `V` in {String, Double, Bool, Day} and carries its table, so `sum` takes a `Field<Double>`, `toggle` takes a `Field<Bool>`, and neither names its table separately. `Spec.FieldValue` pairs a field with a value and has only a generic `init(Field<V>, V)`, so a kind mismatch does not compile. The same type serves an action's values, a sample row, and a query's `where`, so "a `where` that compares a bool field to a string" cannot be built. `window` sits only on the query cases that read a window, so a windowed streak or `daily` cannot be written. `streak` and `daily` take a `Measure`, a table's rows or a `Field<Double>`'s sum, so a sum over a text field cannot be built either. Whether a button needs a `rowId` is derived from the effect (`rowUse`), and whether it needs a `day` likewise (`needsDay`), so the validator and `perform` cannot disagree. All initializers are `internal` to `Spec`, so no other target can construct an unvalidated value. The references that cannot be typed (look to action, look to asset, tap to row) cross a boundary at runtime. They are checked there every time: by the tree validator on every render, which also requires a button's `rowId` to be a row the look actually received for that action's table, and by `perform` on every tap. Every parse failure is one line a model can act on, naming the path and the valid choices: `query "today": no table "glass" (tables: glasses)`.

**The row store.** Six synced tables: `revision(digest, body, saved_at)`, `widget(key, head, ...)`, `history`, `binding(widget, tbl, dataset, stamp, replica)`, `row(key, dataset, day, at, stamp, replica, deleted, deleter)`, and `cell(row, dataset, field, kind, value, stamp, replica)`, plus the local `replica(id, clock)` and `proved(revision, verdict)`. Revisions are immutable and content-addressed, so inserting one twice is a no-op. The head is whole-widget LWW.

**Typed cells.** Each cell stores its kind (text, number, bool, date) beside its value, and a read takes a cell only when its kind is the field's kind: in a list, a `where`, a `sum`, a `daily` or `streak` measure, a sort, and the toggle's read of the current value. So a field a later revision redeclared reads as blank on every path, local, restored, or synced, and a bool `true` never reads as the number 1 or the date 1970-01-02. A missing bool still reads as false. This needs no schema table and no new conflict rule. The builder also checks a new field kind against the kinds already stored in the live rows of each dataset the widget is bound to (`RowStore.storedKinds`), so cells written by a deleted widget, another device, or another user keep their meaning. A field with no cells may change kind, since nothing can be misread.

**Every row change names its dataset.** `insertRow`, `setCell`, and `deleteRow` each carry the dataset they claim, and a row is identified by (key, dataset): the row table's key is that pair, a tombstone that arrives first stores the dataset its delete named, and a cell stores the dataset it claimed and is read only with a row of that dataset. So a change reaches only the row of the dataset it names, or waits for that row when it is not here yet, and a change the server authorized for dataset B never touches a row of dataset A, in any arrival order. Keying by the pair, rather than guarding a key-only row with a check at merge time, is what keeps this convergent: two changes that claim different datasets for one key land on different identities, so neither can outrank the other. `Change.scope` is derived: `.dataset(key)` for row changes, `.account` for revisions, head moves, widget deletes, and bindings. `RowStore.changes(after:)` returns the feed grouped by scope, so the server routes each dataset to its members and account state only to the user's own devices. Bindings never leave the account.

**Remote input is bounded.** `receive(_:now:)` holds back changes stamped more than 10 minutes ahead of the local clock and returns them, so the sync layer offers them again later. It neither merges nor clamps them, since clamping would make replicas disagree, and the local clock does not advance past them. It also refuses text cells over the text limit, through the same `Spec` rule a parsed value obeys, so a peer or an automation cannot pass the limits a tap obeys.

**Remote designs are proved before they draw.** A local save marks its revision proved in the unsynced `proved` table. A widget draws its head when the head passed its proof here, and otherwise its newest revision in `history` that did. With none, it stays hidden. `Engine.proveReceived()` runs the same `prove(..., stopAtFirstFailure: true)` as `build` on every unproved head, for one's own other devices and for a shared widget alike, and records the verdict. The revision is proved exactly as stored, since its canonical bytes are what its digest names. A rejected revision is never drawn. The extension never proves, so it shows the last proved revision meanwhile. A revision this build cannot parse, or whose asset files have not arrived, gets no verdict and is tried again later.

**Rows belong to datasets, not widgets.** A dataset is the rows of one table. Each widget binds each of its table ids to a dataset, and a binding is LWW per (widget, table) and syncs like a head move. A save mints a dataset for every table the widget has no binding for and keeps every existing binding, including those of tables a later revision dropped, so a restore reconnects their rows. So a new widget sees no difference, while two widgets can read and write the same rows: a dashboard over the water log, or later a system-filled dataset such as steps. This was decided before any store shipped (2026-11-20), because after sharing ships the same change is a migration of every user's rows and a new sync format. Field kinds are checked at build against every other live widget bound to the same dataset, the same rule a refinement already followed, and against the kinds already stored in it. Queries resolve the binding as a scalar subquery, so the partial index `row_live(dataset, day, at)` still serves every read, and a table with no binding reads nothing and ignores inserts. Counters are append-only rows. Per-field LWW is one SQL upsert guarded by `(stamp, replica) >`. Deletes are tombstones. Every local write becomes stamped `Change` values merged through one internal function, and later sync will feed remote changes through the same function. Every change kind is idempotent and commutes across keys, so a replay or a double merge changes nothing (per make-operations-idempotent). What sync needs today is all present: device-minted UUIDv7 row keys, a stamp and replica on every cell and tombstone, revisions fetchable by hash, and a change feed that is just `replica = me AND stamp > watermark`, grouped by scope. Day windows use the writer's local calendar day, stored as an integer at insert. A query gets its clock and calendar only through a `Today` value computed once per call from the caller's instant and the engine's calendar. Every window ends today: `today` is `day = t`, `week` runs from the calendar's first weekday, `month` from the first of the calendar month, `all` from the first row, and `{ days: N }` is the last N days. So a row written ahead for a later day, as the server will write a week of words, shows on its day, and the midnight timeline entry flips to it with no network. `daily` groups by day over the last N days, and `streak` groups by day and keeps the days whose row count or field sum reaches its goal. `where` compares one cell for equality, with a missing bool cell counting as false, and may also keep rows by author. A row's author is the replica that inserted it, which the row already stores, so `by` and `where by` need no new column and nothing new to sync. `me` is relative to each store, so two replicas agree on who wrote a row but each calls its own rows `me`. Names live in a local `member` table that only sample seeding fills today and that sharing will fill from the server. `me` means the person, not the install, and that is what the model is taught. Today the engine approximates it with this store's replica, which is exact while a person has one device and no automation has written a row. Sharing must keep the promise: it maps every replica of the person's account to `me` (a second device, a reinstall), and the automation scheduler writes under the owner's account, so a word of the day or a daily question counts as the owner's own row and as another member's on a partner's phone (phase 1e, 2026-11-22).

The grammar grew inside format 1: `where by`, sample `minutesAgo` and `by`, and the reserved field ids `at`, `by`, and `minutesAgo`. No build has shipped, so no stored revision or older peer can hold a field with those ids or misread the new keys, and a format bump would only rename every revision. Any later grammar change after the first TestFlight build bumps `format`. Every query for a render runs in one read transaction. `Rows` also owns content addressing: it hashes asset bytes and revision bodies itself, so a name always matches the bytes it names.

**Two processes.** All of it lives in `Rows`, in one place. Both processes open a WAL `DatabasePool` with a busy timeout and GRDB's suspension handling. Every write is one short immediate transaction. The replica id and the clock live in the database and advance inside that transaction, so writes from the app and the extension are totally ordered without IPC (per separate-before-serializing-shared-state: they write disjoint keys or commutative LWW cells). Either process may migrate, because after an app update the extension can open the file first, and migrations are transactional and idempotent. Each state has a single writer kind: the extension writes rows and cells only, and the app owns revisions, heads, asset files, proof verdicts, and collection. Asset files are immutable, content-addressed, and written before the revision that references them commits. The app's `Engine` takes an `onCommit` hook that reloads WidgetKit after every write, so no app call site can forget to. The extension passes none, because WidgetKit reloads after an intent on its own.

**The JavaScript boundary** is strings: `Sandbox.run(source, context: json, budget:) -> json`. It is a concrete actor, not a protocol, because only one engine ships: QuickJS-ng (see below). The sandbox makes impurity loud (`Math.random` and `Date.now` throw) and enforces a step and a memory budget. The builder rejects a look that exceeds the proof's budget. A look that runs away after it shipped stops at the widget's budget on every reload, its thread ends, and the widget shows a fallback face, so there is no quarantine table. The contract on either side of the boundary (what `ctx` contains, and what a tree may contain) lives in `WidgetEngine` beside the renderer, so the taught shape and the enforced shape have one owner. Tree validation is one function, `Drawing.parse`, run on every widget render and every proof render. Its output, `Drawing`, has no invalid states, so the renderer has no error paths and a failure anywhere upstream becomes a calm fallback face.

**Buttons.** A `Drawing` button holds a `Press`: `.run(tap)` for an action that writes in place, `.form(tap)` for one that asks for input. The renderer hands `(tap, label)` to `FaceHost.button` or `FaceHost.form` and the root `(content, background)` to `FaceHost.root`, and knows nothing else. `WidgetHosting` supplies `Button(intent: RunAction(tap))`, a `Link` to a URL the app handles, and `containerBackground`. The app supplies closure buttons, and proofs use `.still`. `accent: true` nodes and images go through `FaceHost.accent` and `FaceHost.tint`, which the widget host maps to `widgetAccentable()` and `widgetAccentedRenderingMode`. `FaceHost` is a struct of closures with three real values, not a protocol. Forms go through a link because a widget cannot show one, and a link that opens the app is the long-standing mechanism. The intent therefore runs in the background only.

**Taps carry their revision.** A `Tap` holds the digest of the revision its button was drawn from, stamped by the tree validator from `Bindings`, and `perform` and `form(for:)` resolve the action as that revision defines it, provided the widget is live and the revision is in its history (`RowStore.revision(_:of:)`). What the user pressed is what runs: a refinement that lands between the render and the press, even one that reuses an action id for another effect, cannot change what the press does. A tap with no revision, a malformed one, or one outside the history is ignored with a log line, like any stale tap; there is no fallback to the head, because guessing is what the rule exists to prevent. Proofs stamp `unsaved`, which is not a digest, since a proof's spec may never be saved and its taps are never performed.

**Render-time caps.** Each cap is enforced on the path the widget and the proof share, so they cannot disagree. `AssetImages` holds a 1.5 megapixel budget for its lifetime (one `faces` call, both entries, or one proof cell); a decode past it holds nothing and the validator fails with one line. It replaced a fit-report rule that only proofs ran, which let live data past the cap. `composeDrawing` refuses a `ctx` over 1 MB of JSON. A parse-time cap of 1,000 field values over `list` and `latest` queries keeps the worst case (1,000 values of 300 UTF-16 units, each at most 3 UTF-8 bytes, about 900 KB) under that cap statically, and text is limited in UTF-16 units, which is what JavaScript holds.

**Proof equals build.** `Engine.proof`, `Engine.proofs`, and `build` share `prove`, which seeds a scratch in-memory store through the real write path and calls the same `composeDrawing` the widget calls. `proof.verdict` is the exact line `build` would send, so the eval tool and the builder cannot disagree about what passes (red flag: two ways to do one task). `Engine.proofs` exists because an eval needs every cell of the matrix, not only the cells up to the first failure, plus a verdict identical to `build`'s. It is `prove` with `stopAtFirstFailure: false`, not a second checker. The render tool takes rows in the samples grammar, not raw `ctx.data`, so evals exercise the query engine too. Besides the empty state and the model's samples, the proof renders `full`, which `Spec` synthesizes from the document: every list at its limit, three-digit counts and streaks, every `daily` day filled, and in every field the longest value the widget can store there. A field that a form or an automation writes gets text at the real limit, 300 UTF-16 units of ordinary words, so the proof renders the largest data a widget can hold, but a field that only fixed action values write gets the longest of those values. The first eval showed why: a mood field written only by five emoji buttons received a 40-character sentence in `full`, which rejected correct looks and pushed models to design for text that can never appear. `full` catches the spills a model's own samples miss. `Spec` owns it because only `Spec` can construct a `Sample`.

**What a render must pass.** The rules are measured on drawn pixels and drawn nodes, because those are what the person sees. Only drawn nodes (text, symbols, shapes, images, buttons) count as spill. A root whose padding or frame runs past the edge cuts nothing, so rejecting it would reject correct looks; `FitReport.layoutOverflow` still reports it. An ellipsis at the look's own `lineLimit` passes in every state, not only in `full`, because it is what the look asked for whatever the data. Text cut short without one is rejected anywhere. The blank check counts sampled opaque pixels that stand out from the most common color by 32 of 255 in some channel, so anti-aliased corners and text one shade off its background are not content, and a look under 0.05% such pixels is blank. `FitReport` is shaped around those rules: `spill`, `edges`, and `cut` for drawn spill, `truncated` (rejected) apart from `ellipsized` (allowed), `ink` for the blank check, and `layoutOverflow` as information only.

**Deliberately not done.** No sync code, no automation execution on the phone, no spec or look cache (parsing a 20 KB document takes about a millisecond), no seed rows, no quarantine table, and no protocol anywhere except `CellType`, which has four conformances. Renders never write.

**Deviations from the decided `ctx`.** Phase 1e added `ctx.now` and, on every row, `at`, `minutesAgo`, and `by`, so shared and "how long ago" widgets need no time or author fields of their own. A look still never reads a clock. The sandbox watches `now` and `minutesAgo` and reports whether the look read either. A look that did is drawn every 15 minutes for two hours, keeping the entries that changed, and the timeline reloads after those two hours. A look that did not costs nothing extra. A single probe 15 minutes ahead was tried first and missed looks that change hourly or at a threshold, such as "fed 11 h ago" turning red at 12 h. Proofs render at noon of the current day, so a verdict does not depend on the hour it runs. I added `ctx.today = { date, weekday, week }`. Users ask for the date on a widget, and looks draw day strips, but a look must not read a clock, so the date has to be an input. History views read the `daily` query instead of bucketing rows themselves. Both are additive.

## Synthesis decision

Two independent designs were produced on 2026-11-18. This design is candidate one with six parts taken from candidate two and five decisions that override both. [SYNTHESIS.md](SYNTHESIS.md) has the full record. This section states what was decided and why.

**Base: candidate one.** It has the smallest interface: one `Engine`, one call per entry point, and builder methods that only `WidgetBuilder` importers see. Its stored local day makes "today" an integer comparison and means travel never breaks a streak. Its render tool and builder share one code path, so an eval and a real build cannot disagree. Its JavaScript boundary is text in and text out, one file to swap.

**Where the two designs agreed without seeing each other.** One stored value per (row, field) with a clock stamp and one merge function. No operation log. Block types only the parser can construct, with typed field handles. A strings-only JavaScript boundary. One tree validator separate from a renderer that cannot fail. A host closure that decides what a button is. A builder target the extension never links. A need for day-bucketed history and for a field filter on queries. That agreement is the strongest evidence in the exercise.

**Taken from candidate two.**

1. The `daily(table, days)` query, so history views need no date arithmetic. `ctx.today` stays too.
2. Content-addressed document revisions with a head pointer, which give undo and sharing.
3. Forms that open the app through a link, replacing an unverified foreground-continuing intent.
4. The synthesized `full` proof state.
5. Button row ids checked against the rows the look was given.
6. A commit hook on the app's engine, and migrations from either process.

**Overrides.**

- `count`, `sum`, `latest`, and `list` take an optional `where`: one field equal to one literal, nothing more. It makes open and done to-dos correct past the list limit.
- The build loop runs on the phone, because fit can only be measured where SwiftUI runs. The backend returns the model's document and never measures fit.
- A shared widget is proved again on arrival, through `build`.
- No seed rows. The empty state is a state every look must handle.
- The builder rejects a look that exceeds the proof's step or memory budget. A shipped look that runs away stops at the widget's budget and draws a fallback face.

**Rejected from candidate two.** A pure fact table with no row record: day windows would need per-read bucketing in Swift, and row existence would become a convention. Days computed at read time in the viewer's time zone: travel would move rows between days. A `ScriptEngine` protocol with two implementations now: add it when the second engine is written for the device comparison.

**No cross-family judge.** The arena calls for a judge from a different model family. None was available, so the base was picked without one.

## Tradeoffs accepted

- We accept `AnyView` at the host seams, in exchange for a renderer that imports neither AppIntents nor WidgetKit.
- We accept running the look twice per timeline (now and next midnight), in exchange for day windows that flip exactly at midnight without spending refresh budget.
- We accept pivoting cells into rows for `list`, in exchange for per-field merge as one SQL statement shared by local and remote writes.
- We accept that a duplicated insert delivery logs twice, and that `toggle` flips the stored value rather than the displayed one. The intent carries no nonce or expected value. WidgetKit delivers each tap once, and it reloads after every tap.
- We accept that a button's `day` is checked twice: the tree validator draws a day outside today and the 365 days before it as untappable instead of failing the look, because a week strip holds days after today on most days, and the store checks the day again against the tap's own today. A tap after midnight still logs the absolute day its button showed.
- We accept that a row lands on its writer's local day, so in a widget shared across time zones a row can show as "tomorrow" for the reader. In exchange, travel never breaks a streak.
- We accept head LWW for edits, so two people refining one shared widget at once lose one head move. The losing revision still exists and can be restored. Data rows still merge per field.
- We accept that every saved revision stays until a collector removes the ones no head or history entry names, in exchange for undo and hash-addressed sharing.
- We accept that a form opens the app instead of finishing on the home screen, in exchange for a mechanism that is known to work from a widget.
- We accept that `where` is equality on one field, so "items due this week" cannot be a query. In exchange, the closed set stays small enough to teach and to check.
- We accept that the builder runs on the phone, so each repair is an app to backend round trip. In exchange, fit is measured with iOS fonts and the exact renderer. The Mac tool's fit can differ where macOS fonts differ.
- We accept that any vocabulary addition bumps `format`, so an older app refuses a newer document even when its look does not use the new nodes. In exchange, failures happen up front with "update the app" instead of mid-render.
- We accept that `Engine.init` cannot fail and the store opens lazily, in exchange for hosts with no error path at construction. The first call reports a failure in its normal channel.

## Alternatives considered

- **Layered public modules (document, store, look, renderer) composed by each host.** Every host would repeat load, query, run, validate, render, in that order. That is temporal decomposition plus leakage of the `ctx` shape and the pipeline into four places. It exposes the most surface and hides the least.
- **One public module including the builder.** One less import line in the app, but the extension would link, and could call, image ingest, PNG encoding, and fit analysis. The split costs almost nothing and makes the boundary a link-time fact.
- **A JSON `fields` column per row with a row-level `updated_at`** (the plan's first sketch). Per-field LWW needs a stamp per field, so this becomes JSON read-modify-write with per-field stamps inside a blob, `sum` needs `json_extract`, and the merge rule moves from one SQL statement into Swift. It hides less and is easier to get wrong.
- **A pure fact table with no row record** (candidate two). Uniform, but day windows then need per-read bucketing in Swift and row existence becomes a convention.
- **An operation log with materialized state and server rebase.** It keeps two representations in sync and needs rebase logic. Append-only counters and per-field LWW already commute, so state-based merge gives the same guarantees with one representation. An outbox can still be added later if the server wants ops.
- **Day windows from instants in the reader's time zone** (candidate two). No stored day, but travel and cross-time-zone sharing move rows between days and break streaks.
- **Asset digests in a column beside the document body** (candidate one before the synthesis). Then a revision's hash would not cover its images, and a shared revision would not name the files it needs.
- **A renderer that emits `Button(intent:)`, is generic over an intent type, or reads an action handler from the environment.** The first two teach the renderer App Intents and force the tool to fake intents. The third is invisible coupling an agent cannot see from the call site.
- **A foreground-continuing intent for forms** (candidate one before the synthesis). One intent for every button, but unverified on a device, and a link is the long-standing mechanism.
- **A `ScriptEngine` protocol with two implementations** (candidate two). Only one will ship. The strings-only boundary already makes the swap a one-file change, and a protocol would outlive the bakeoff as dead abstraction.
- **A model reply format separate from the stored and shared document.** Two grammars and two parsers. A single exchange format, with the few fields the builder fills in, is simpler and gives refinement for free.

## JavaScript engine: QuickJS-ng

JavaScriptCore cannot interrupt a script, so its timeout abandoned a spinning thread and its VM until the process exited, nothing capped memory, and budgets were milliseconds measured on a Mac with a JIT that no third-party iOS app gets. `Sandbox` now runs looks on QuickJS-ng, vendored unmodified in `Engine/Vendor/QuickJS` as the C target `CQuickJS` (tag `v0.18.0`, MIT, only the engine library: no `std` or `os` module, no CLI). JavaScriptCore is gone, and the boundary is unchanged: strings in, string out, the same `Failure` cases, the same prelude.

- **Fresh runtime per run.** Each run creates a runtime and context and frees both before it returns, on its own thread with a 4 MB stack. The thread always ends, because every cap below stops the script on that thread.
- **Steps, not time.** QuickJS calls an interrupt handler once every 10,000 interpreter checkpoints (backward jumps, calls, loops inside some built-ins, regular expression backtracking). One step is one call. The count starts at zero each run and depends only on the look and its context, so the Mac and the phone give the same verdict. Past the budget the handler raises an error the look cannot catch.
- **Memory.** A metered allocator counts every byte the runtime holds from the system allocator, built-ins included, and refuses requests past the budget. `JS_SetMemoryLimit` was not enough: when its cap is hit QuickJS often cannot allocate the error either and throws `null`, which looks like the look's own `throw null`. A run that met a cap fails with that cap's line even if the look caught the error.
- **Stack.** The script stack is capped at 1 MB, so runaway recursion throws a `RangeError` with its look line. That is about 1,000 to 2,000 levels in a release build and about 280 in a debug build. The prelude's tree walk keeps its own stack, so the 200-level depth check uses none.
- **Budgets.** `widget` is 2,000 steps and 12 MB. `proof` is 500 steps and 8 MB, stricter so a proved look survives real rows outgrowing the samples. Every reference look and fixture takes 1 step and 229 to 256 KB, about 210 KB of which is the runtime itself.
- **Failure lines.** "look ran longer than 500 steps; render(ctx) must finish quickly, so look for an endless loop", and new: "look used more than 8 MB of memory; render(ctx) must build a small tree, so look for a loop that keeps growing an array or string". Exception messages are QuickJS's own, such as `cannot read property 'title' of undefined`.

Measured on this Mac (Apple M4, C built at -O2 as in release), JavaScriptCore against QuickJS:

| | JavaScriptCore | QuickJS-ng |
|---|---|---|
| Sandbox run, warm, per fixture render (median of 300) | 86 to 152 µs | 219 to 376 µs |
| Look time in `render-tool proof`, median over 32 renders and 15 runs | 0.85 ms | 0.85 ms |
| First look in a process (cold) | 47 to 50 ms | 38 to 40 ms |
| Process footprint after the first run / after 1,000 more | +3.4 MB / +3.1 MB | +0.4 MB / +0.5 MB |
| Endless loop returns, widget / proof budget | 266 / 105 ms, thread spins forever | 33 / 8 ms, thread ends |
| Footprint after 10 endless loops | +4.1 MB | +0.03 MB |
| `render-tool` peak RSS for a proof | 57 to 59 MB | 53 to 55 MB |
| `render-tool` release binary | 7.5 MB | 8.6 MB |

A step costs 16 µs in an empty loop and about 64 µs in a loop doing float arithmetic. QuickJS is slower per run because it builds the runtime and parses the prelude every time, which is a cost paid for zero shared state. All 32 fixture PNGs and the four `report.json` files (timing fields aside) are byte-identical before and after the swap, and `leaks` finds nothing after proofs or after looks that loop, run out of memory, or throw.

The device bakeoff still has to confirm: the time per step on an iPhone, and so whether 2,000 steps stays well inside a widget reload; that a runaway look at 12 MB plus a full render stays inside the 30 MB extension; and the cold first run in the extension process.

## Open questions and risks

- QuickJS-ng on a device. Decided: QuickJS-ng with step and memory budgets replaced JavaScriptCore, so a runaway look that ships stops at its budget and its thread ends, and no quarantine is needed. Open: the time per step, the memory peak inside the 30 MB extension, and the cold first run, measured on an iPhone.
- Tinted and dark mode. They are known only inside the view, never to the provider, so one tree must work in every mode. Decided: colors may be `{ light, dark }` pairs resolved from the view's color scheme (dark mode stays optional, so a look may keep its own colors), any node may set `accent: true`, an image sets `tint`, and the renderer reads a package `RenderingMode` environment value that the widget host maps from `widgetRenderingMode`. In accented mode the renderer draws what the system is expected to draw (backdrop, white at each node's opacity, tint for accent nodes, images by `tint`), so proofs and the widget run one code path, and the system's own recolor by opacity should leave it unchanged. The proof checks tinted renders for blanks and for a backdrop drawn as a full-size shape. Clear mode on the simulator (2026-11-21) draws accent nodes in the same color as the rest, so a mark on an accent disc vanishes there; `look.md` now teaches cutting the mark out of the shape. Open: whether the device matches the emulation in tinted mode. Needs a device.
- Should an automation see its table's recent rows, so word of the day does not repeat? In the first eval, 3 of the 4 automation prompts the models wrote asked the writer not to repeat earlier rows, which it cannot honor today. Models also tried to add a "new one now" button, and no action can ask an automation for a row on demand.
- The backend must read part of the grammar (automations, table schemas) and teach the whole of it to the model. Should a test generate a JSON Schema from the Swift types, with backend CI failing on a diff, so the two languages cannot drift? `Engine/Reference/blocks.md` is already parsed by a test, which covers the teaching half.
- SF Symbol sets differ between macOS and iOS. A Mac proof can accept a symbol the phone lacks, which then renders as a fallback face on device. Proving on the phone during the in-app build and on arrival of a shared widget covers users, but evals run on the Mac.
- A form link needs a URL scheme the app registers. Does a link from a widget open the app on the form without a visible delay on iOS 26? Needs a device.
